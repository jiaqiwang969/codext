# 从 daemon 管理切入：Superagent 融入日常 Codext daemon

版本：设计讨论稿 v0.1，2026-11-04。状态：**设计候选，未实施。**

配套材料：[架构梳理讨论稿](superagent-command-center-architecture.md)、[接手调研补充](superagent-command-center-research.md)。代码路径默认相对 `codex-rs/`。

## 0. 目标与约束

用户要求（2026-11-04）：

- 在 Mac 上搭；
- 与原有 Codext 协同；
- 从 daemon 管理的角度切入；
- Superagent 的架构体系都能融合进去。

据此，本设计满足五条约束：

1. **只有一个 daemon。** 日常的 managed daemon 同时承载普通会话、Router 主线、由引擎推进的会话和原生 helper，不另起组织专用的 app-server。
2. **功能关闭时行为与现在完全相同。** 打开后，未纳管会话的行为也不变。
3. **同一个根会话，任一时刻只有一个驱动者。** 这是协同的核心规则。
4. **Superagent 的协调机制全部在 daemon 进程内运行**：账本、投递、恢复、点名、退回、预算、守卫、槽位、巡检。
5. **不依赖 ATM 和 Dell**，不迁移 Dell 上封存的旧工单。

## 1. 现状：daemon 已有的管理能力和唯一的硬阻塞

| 能力 | 现状 | 位置 |
| --- | --- | --- |
| 生命周期 | start、restart、update、stop；自动更新器在启动 5 分钟后检查一次，之后每小时一次，有更新时会重启 | `app-server-daemon/src/lib.rs` |
| 优雅停机 | 第一次停机信号拒绝新回合，等待运行中的回合；第二次可强制退出 | `app-server/src/lib.rs:259-327, 1076-1130` |
| 计划内重启的恢复 | 停机时写快照；启动后对快照中的线程做冷恢复，对被中断的回合续跑一次 | `request_processors/daemon_snapshot.rs`、`daemon_thread_recovery.rs`、`daemon_continuation.rs` |
| 加载与卸载 | 无订阅者的空闲线程 60 秒后卸载 | `request_processors/thread_lifecycle.rs` |
| 自动驱动 | 持久队列、Goal、多 agent 邮箱唤醒、记忆整理，加上客户端 TUI 的自动发送 | 见 §3 |
| 账号 | 每个线程有自己的账号运行时，空闲时可真实切换 | `request_processors/thread_auth_profile.rs` |
| 功能开关 | daemon 拉起子进程时，把 `settings.json` 的 feature overrides 转成 `-c features.*` 参数 | `app-server-daemon/src/backend/pid.rs:393-426` |
| 面板 | `codext agents` 强制使用 managed daemon | `cli/src/main.rs:2567-2584` |

引擎这一侧已经具备的条件：

- 按功能开关加载；
- 先对账再分发；
- 停机时先停调度，再等在途投递结束；
- 扩展注册顺序是 queue → superagent → goal（`app-server/src/extensions.rs:91-112`）。

**唯一的硬阻塞**在 `app-server/src/lib.rs:603-607`：managed daemon 一旦打开 superagent 就会拒绝启动。原因在引擎自己的说明里写得很清楚（`ext/superagent/src/recovery.rs:19-35`）：

- worker 是持久根线程，会被 daemon 快照收录；
- daemon 的续跑没有按线程关闭的开关；
- 结果是它会和引擎的对账同时续跑同一个 worker。

本设计要解决的就是这一点，同时处理调研补充 F13–F15 指出的其他自动驱动。

## 2. 核心概念：驱动权

每个根线程都有一个**驱动者**，由协调账本持久保存：

| 驱动者 | 含义 |
| --- | --- |
| `native`（默认） | 现状。用户、Goal、队列、daemon 续跑都可以按原规则启动回合 |
| `engine` | 由推进器驱动，绑定某个目标或工单。只有引擎能启动自动回合 |
| `human` | 用户临时接管。引擎暂停对它的调度，等用户交回 |

驱动权是协调账本里的一张表。除了引擎自己，没有其他写入方。另外在线程附件中镜像一份，便于面板和 `thread/read` 显示。

### 2.1 唯一的仲裁点

所有原生自动驱动最终都进入同一个函数：`CodexThread::submit_turn_input_with_mode`（`core/src/codex_thread.rs:652`），以 StartIfIdle 或 ContinueIfIdle 模式启动回合。调用方包括：

- 队列：`ext/queue/src/service.rs:392, 440`
- Goal：`ext/goal/src/runtime.rs:491`
- 多 agent 邮箱：`ext/agent/src/lib.rs:79`
- 记忆整理：`memories/write/src/runtime.rs:430`
- daemon 续跑：`request_processors/daemon_continuation.rs:120`

建议在这条自动路径上增加一个按线程的仲裁钩子：

- 在 `codex-extension-api` 中新增一个 trait，例如 `AutomaticTurnArbiter`，带完整的文档注释，返回值采用显式 `Send` future。
- 输入是线程的扩展存储和本次回合的 `turn_trigger`，输出为允许或拒绝。
- 引擎实现这个 trait：对 `engine` 驱动的线程，只放行引擎自己的触发；对 `human` 驱动的线程，拒绝所有自动触发；对 `native` 线程一律放行。
- 功能关闭时没有仲裁者，路径与现在相同。

对 codex-core 的改动只有一次调用，与现有的 `admit_turn_start` 并列。这比分别修改队列、Goal、daemon 续跑三处更可靠：以后新增的自动驱动，也会自动经过同一个检查点。

这里有一个前提：每种自动驱动都要带上明确的 `turn_trigger`，否则仲裁者无法区分来源。实施时需要逐一确认队列、邮箱和记忆整理是否已设置触发标识。

### 2.2 客户端发起的回合

用户在面板或 TUI 里直接给 `engine` 驱动的线程发消息时，这是人的输入，应当**允许**。处理分三步：

1. 引擎在回合开始时把这条输入记为对目标的纠正（这需要先修好 G01）；
2. 驱动权临时转为 `human`，直到这个回合结束；
3. 下一次起草时，必须处理这条纠正。

TUI 在额度恢复或切号后会自动发送一条暂存的"合成恢复提示"（`tui/src/chatwidget/turn_runtime.rs:481-495`）。这条提示不是人写的，对非 `native` 线程应当由客户端跳过。判断依据是线程附件里镜像的驱动权。

### 2.3 查看不等于恢复

resume 结束时会发出空闲事件，从而触发自动驱动（调研补充 F13）。面板查看 `engine` 驱动的线程时，只用 `thread/read` 和 `thread/turns/list`。只有用户明确选择"进入"或"接管"时才 resume；而且恢复后产生的空闲事件，也已经由 §2.1 的仲裁点拦下。

## 3. 线程所有权表

| 线程类别 | 冷加载 | 被中断回合的续跑 | 空闲时的自动驱动 | 停止与清理 | 进入 daemon 快照 |
| --- | --- | --- | --- | --- | --- |
| 普通会话（`native`） | daemon 或客户端 | daemon 续跑，与现状相同 | 队列、Goal、邮箱、TUI，与现状相同 | 用户 | 是 |
| Router 主线 | daemon 或客户端 | 由引擎在对账后决定 | 只处理用户消息和需要上报的事项；不开 Goal | 用户 | 是，但续跑被仲裁点拒绝 |
| 引擎推进的会话（`engine`） | 引擎投递前恢复；daemon 也可以冷加载，冷加载本身没有副作用 | 只由引擎对账决定：结果不明的投递等人处理，忙碌中断的带恢复说明重启 | 只有推进器；队列只作为投递通道；Goal、daemon 续跑和 TUI 自动发送都被拒绝 | 引擎：中断回合、清理后台任务、收尾 helper | 是，但续跑被仲裁点拒绝 |
| 用户接管中的会话（`human`） | 用户客户端 | 不自动续跑 | 全部拒绝，等待用户 | 用户；交回时引擎重新读取根请求与纠正 | 是 |
| 原生 helper | 经父会话 | 不续跑（快照本来就排除） | 父会话的邮箱 | 父会话；引擎只能通过它所属的 worker 间接处理 | 否 |

## 4. 启动、停机与重启顺序

### 4.1 启动（start、restart、update、自动更新）

1. 读取配置和功能开关；如果打开了 superagent，打开协调账本，**先载入驱动权表**。这一步数据量小，可以同步完成。
2. 注册扩展并构建处理器。仲裁者从这一刻起就生效：对账本中登记为 `engine` 或 `human` 的线程，在引擎宣布就绪之前，拒绝一切自动回合。
3. daemon 恢复任务按快照冷加载线程。普通会话照常续跑；非 `native` 线程的续跑被拒绝，记录一条"交由引擎对账"。
4. 引擎对账（现有逻辑，`ext/superagent/src/recovery.rs`）：重新排队、带恢复说明重启、标记等人处理。同时清理它自己写入队列、但已不应执行的投递（见 §5）。
5. 引擎宣布就绪，推进器、巡检和发件箱开始工作。

崩溃或 SIGKILL 时没有快照，第 3 步为空，只剩第 4 步。这正是引擎原本的设计，不需要额外处理。

### 4.2 停机

现状是：先写快照，等运行中的回合结束后，才让引擎排空（`app-server/src/lib.rs:1082-1126, 1384`）。在两者之间，引擎仍可能尝试投递。

建议改为：

1. 收到停机请求后，**先停止引擎调度**，并等待已开始的投递结束；
2. 写快照；
3. 等待运行中的回合；
4. 关闭线程。

快照仍然收录非 `native` 线程，以便重启后加载，但它们的续跑由引擎决定。

## 5. 持久队列：保留为唯一的投递通道

- 引擎写入的队列项加上来源标记（引擎、目标或工单、指派、投递 id）。
- 对账时，用 `thread/queue/list` 和 `thread/queue/delete` 删除那些对应"结果不明、等人处理"或"已被新指派取代"的引擎队列项。这样就修复了 G02："不盲目重放"的承诺真正覆盖到队列。
- 用户手动排队的项不受影响。但在 `engine` 线程上，它们只在驱动权转为 `human` 或回到 `native` 时才会发送；具体规则交给评审决定。

## 6. Goal、账号与配置

- **Goal：** 纳管时，如果线程已有 Goal，就把目标原文转入工程本体的锚定记录，再清除原生 Goal（需要用户确认）。之后仲裁点会拒绝 `goal` 触发。如果评审选择保留 Goal 仅作展示，也可以，因为它已无法启动回合。
- **账号：** 给 `engine` 线程切号，仍走现有的真实切号流程，只是限定在没有在途投递时进行。切号完成后，引擎更新自己的账号负载计数（修复 F24 的计数漂移）；面板上的 ⇧P 对 `engine` 线程应提示由引擎执行。
- **配置：** 引擎参数目前读取 `CODEXT_SUPERAGENT_*` 环境变量。daemon 子进程拿不到这些变量，而且它们在 daemon 启动时就固定了。建议迁到 `config.toml` 的 `[superagent]` 段，并按 `ConfigToml` 规则更新 schema。同时删除 Dell 的默认值（G08）：根目录、仓库和账号池都改由项目注册表和账号工具提供。功能开关沿用 `settings.json` 的 feature overrides，这样 daemon 重启后仍然生效。

## 8. 分阶段实施

每个阶段结束时，现有 Codext 都必须照常可用；关闭功能就回到上一阶段。

| 阶段 | 范围 | 对日常使用的影响 | 退出条件 |
| --- | --- | --- | --- |
| P0 基础 | 仲裁钩子（功能关闭时为空操作）；驱动权表与线程附件镜像；配置迁入 `config.toml`；调整停机顺序；修复 G01–G03；在功能开关下移除 lib.rs 的拒绝 | 功能关闭时无变化 | 功能关闭时行为与现状一致；打开但没有纳管任何线程时，所有会话行为不变 |
| P1 只读接入 | 日常 daemon 中打开引擎，不纳管任何线程。Router 主线达到"看见"档：只读索引所有会话；面板显示 Router 和索引 | 只增加一个 Router 会话，不自动发送任何内容 | 面板查看任何会话都不触发回合；daemon 重启和更新不产生额外回合 |
| P2 纳管与推进 | 驱动权的获取、释放、接管、交回；推进循环接入工程本体判定；队列项打标签并在对账时清理 | 只影响用户明确纳管的会话 | §9 的验收全部通过 |
| P3 派工与项目 | 引擎在项目目录里新建 worker（非 Git 可用）；新建 `~/编号-名称` 项目；helper 收尾；槽位按项目和账号划分 | 同上 | 多项目并行时无串项、无重复续跑 |

当前分支的重做规则禁止新增测试。P0 之前需要先确定实施分支和验证规则（调研补充 D15）。

## 9. daemon 视角的验收

- 功能关闭：日常会话、队列、Goal、daemon 重启续跑、切号和面板，行为与现状一致。
- 计划内重启（restart、update、自动更新）时，`engine` 线程上正在运行的回合：恰好得到一次续跑决定，而且是引擎做出的；不会出现 daemon 续跑与引擎重启并存。
- 崩溃重启（没有快照）：只有引擎对账，没有任何遗漏或重复。
- 结果不明的投递：引擎写入的队列项在用户确认前被清理，任何 resume 都不会执行它。
- `engine` 线程上残留的 Goal 不会启动回合；TUI 的合成恢复提示不会发给它。
- 用户在 `engine` 线程里直接输入：回合正常执行；输入记入目标；驱动权临时转为 `human`；回合结束后，下一次起草处理了这条纠正。
- 面板查看 `engine` 线程：不启动任何回合。
- 切换 `engine` 线程的账号：只在没有在途投递时允许；引擎的账号负载计数随之更新。
- 停机期间：先停调度再写快照，没有在快照之后才开始的新投递。

## 10. 开放问题

1. 仲裁钩子放在 codex-core 的自动启动路径（改一处，覆盖全部自动驱动），还是分别修改队列、Goal 和 daemon 续跑（不碰 core，但容易遗漏）？本稿推荐前者。
2. `engine` 线程上用户手动排队的消息怎么处理：立即作为人工输入发送，还是等交回后再发？
3. Router 主线本身是否允许被 daemon 重启续跑？本稿建议交由引擎决定，以免重启时与待处理事项冲突。
4. 驱动权的正本放在协调账本，线程附件只作镜像：出现不一致时以账本为准。是否接受？
5. 实施分支与验证规则（D15）怎么定：是在当前重做分支外另开开发分支，还是在本分支内按"只构建"的规则推进？
